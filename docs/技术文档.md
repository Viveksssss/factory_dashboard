## 1. 项目概述

### 1.1 项目定位

面向模具制造 / 精密加工车间的**生产数据实时监控大屏**，挂在车间大屏显示器上，
用于展示当月计划达成率、模具进度、送检一次合格率、品质管理等关键指标。

### 1.2 技术选型

| 项目 | 选型 | 理由 |
|---|---|---|
| 框架 | Qt 6.5+（Widgets 模块） | 目标环境为 Windows 工控机，需离线运行；Widgets 的 QPainter 绘制能力最适合自绘图表 |
| 语言标准 | C++17 | `if` 初始化、`std::optional` 等现代特性 |
| 图表方案 | QPainter 全自绘 | 见下方说明 |
| 构建 | CMake 3.16+ | Qt 官方推荐，跨 IDE 一致 |
| 第三方依赖 | **零** | 只需 Qt 本身，编译环境简单，便于交付 |

### 1.3 为什么不用 Qwt / QChart？

这是本项目最核心的技术决策，值得展开说明：

**QChart 的问题**
1. `QtCharts` 模块在 Qt 6 中已被标记为「不再积极维护」，且 Qt 官方明确建议新项目使用其他方案。
2. 样式定制能力弱。本设计稿要求的**沿圆弧渐变刻度**、**双层半透明发光**、**七段数码管的六边形段体**、
   **逐柱异色**等效果，用 QChart 实现需要大量 QSS 覆盖内部 private 字段，代码脆弱且跨 Qt 版本易失效。
3. QChart 内部使用 QGraphicsView 场景图，对 20+ 图表同屏刷新场景偏重。

**Qwt 的问题**
1. 不是 Qt 官方模块，版本适配需手工处理，容易与 Qt 版本冲突。
2. 样式仍然以「配置项」形式暴露，无法表达「这个圆弧的第 37 度到第 52 度要用渐变」这类需求。
3. 体积较大，引入即增加部署复杂度。

**自绘的代价与收益**

代价：需要自己实现坐标映射、刻度计算、字体排版、图例等工作，约 2000 行代码。

收益：
- **表现力无上限**：设计稿的任何一个细节都能 1:1 复刻，不受库的抽象限制。
- **性能可控**：可以精确控制绘制顺序、减少不必要的状态设置。QPainter 的直接绘制比场景图遍历更轻。
- **零依赖**：只需 Qt 6，交付时拷贝可执行文件 + Qt 运行库即可。
- **技术深度**：这是面试中展示 Qt 底层绘制能力的最佳载体（详见第 12 章）。

### 1.4 代码规模

| 模块 | 文件数 | 行数 | 说明 |
|---|---|---|---|
| `core/` | 4 | 516 | 主题系统、等比缩放画布 |

## 2. 需求拆解与设计还原

### 2.1 设计稿的量化分析

复刻的第一步不是写代码，而是**把设计稿量化**。
项目提供了两个分析脚本，用于从参考图中提取精确的布局与配色数据：

```bash
python tools/analyze_layout.py    # 提取栏/行的边界比例
python tools/analyze_rows.py      # 精确定位每个面板的上下边界
python tools/scale_layout.py      # 换算到 1920x1080 设计坐标系
```

**分析思路**：面板区域填充色为 `#26294A`，栏间缝隙是大屏底色 `#040726`。
因此计算「每列被非底色像素占的比例」，出现断崖式下跌的位置就是栏边界。

**关键发现**：参考图原尺寸为 **2265 × 1218**，宽高比 1.86（并非 16:9）。
三栏宽度占比为 609 : 826 : 476。换算到 1920×1080 后得到本项目使用的坐标表。

### 2.3 配色的量化还原

所有颜色**逐像素采样自参考图**，而非凭经验估计。采样方法：

```python
# 对某区域统计所有「高饱和度」像素（max-min > 55，即有明确色彩倾向）
def brightest(box, name, thr=55):
    counter = Counter(im.crop(box).getdata())
    s = [(c, n) for c, n in counter.items() if max(c) - min(c) > thr]
    s.sort(key=lambda t: -t[1])
    return ['#%02X%02X%02X' % c for c, _ in s[:8]]
```

得到的核心色板：

| 用途 | 色值 | 采样位置 |
|---|---|---|
| 大屏底色 | `#040726` | 栏间缝隙 |
| 面板标题栏 | `#303056` | 各面板标题条 |
| 面板主体 | `#26294A` | 各面板内容区 |
| 主强调·青 | `#00B0B5` | 柱体、进度环、飞线 |
| 主强调·蓝 | `#0071C0` | 柱体、折线 |
| 警戒黄 | `#FFC000` | 超标柱体、饼图扇区 |
| 危险红 | `#FE0000` | 不合格柱体、饼图扇区 |
| 完成绿 | `#00AF50` | 合格扇区 |

```
DashboardData（纯数据）  ──setData()──>  ChartWidgets（纯绘制）

（可替换为 HTTP/MQTT/DB）
```

**收益**：
1. 同一套 `GroupedBarChart` 既能画「零件达成率」（双系列），
   又能画「班组合格率」（单系列逐柱异色）——控件完全不知道自己画的是什么。
2. 接入真实后端时，只需实现一个发 `dataUpdated()` 信号的数据源，UI 层零改动。
3. 数据可独立进行单元测试。

### 3.3 坐标系约定

| 坐标空间 | 说明 |
|---|---|
| **设计坐标** | 1920×1080，全项目所有面板坐标写死于此 |
| **窗口坐标** | 实际屏幕像素，由 `ScaledCanvas` 换算 |
| **地图归一化坐标** | 经纬度投影后的 0~1 相对值，再由 `ChinaMapWidget` 映射到控件矩形 |

分离这三套坐标是项目结构清晰的关键：布局代码不需要关心屏幕分辨率，
地图代码不需要关心像素，缩放逻辑集中在一处。

## 4. 核心机制：等比缩放与离屏渲染

这是本项目技术上最值得讲的一节。

### 4.1 问题

大屏要跑在 1920×1080 / 2560×1440 / 3840×2160 等不同分辨率上。

- 按实际像素硬编码布局 → 换分辨率就错位。
- 用 `QLayout` 自适应 → 面板宽高比变化，**圆形仪表被拉成椭圆**，
  进度环变椭圆，柱状图比例失调。大屏对「图形不变形」的要求是刚性的。

### 4.2 三个方案的取舍

**方案 A：逐个 `setGeometry` 缩放子控件**

```cpp
for (QWidget *w : children())
    w->setGeometry(w->x() * scale, w->y() * scale,
                   w->width() * scale, w->height() * scale);
```

- ✅ 实现简单
- ❌ **文字字号和线宽不会跟着放大**。在 4K 屏上，同样的 12px 文字只占设计尺寸的一半，
  视觉上又小又细，与 1080p 效果完全不同。
- ❌ 每次 resize 都要遍历所有子控件

**方案 B：直接用 painter 变换画整个画布**

```cpp
void paintEvent(QPaintEvent *) {
    QPainter p(this);
    p.scale(m_scale, m_scale);
    paintContent(&p);      // 但子控件是真实 QWidget，不参与这个变换！
}
```

- ✅ 缩放逻辑简单
- ❌ **致命问题**：面板是 `QWidget` 子窗口。Qt 会在 `paintEvent` 返回后，
  用子控件的**原生几何**（1920×1080 未缩放）**再画一遍**。
  结果在 2560×1440 上会看到「缩放版 + 未缩放版」两套画面叠加，左上角 1920×1080 区域
  有一个清晰的未缩放矩形边界。

> 这正是本项目第一版的实现方式，由代码审查发现并修复。

**方案 C：离屏容器 + render()（最终采用）**

```cpp
// 1) 容器不作为窗口子控件显示，彻底绕开 Qt 的自动绘制
m_content = new QWidget(nullptr);
m_content->setAttribute(Qt::WA_DontShowOnScreen, true);
m_content->setFixedSize(1920, 1080);

// 2) 渲染到离屏 QImage
void rebuildCache() {
    m_cache = QImage(1920, 1080, QImage::Format_ARGB32_Premultiplied);
    QPainter p(&m_cache);
    m_content->render(&p, QPoint(0, 0), QRegion(),
                      QWidget::DrawWindowBackground | QWidget::DrawChildren);
}

// 3) 缩放后贴到屏幕
void paintEvent(QPaintEvent *) {
    painter.fillRect(rect(), bgColor);
    QRectF target(m_offset.x(), m_offset.y(), 1920 * m_scale, 1080 * m_scale);
    painter.drawImage(target, m_cache, QRectF(m_cache.rect()));
}
```

**为什么方案 C 是正解**：

1. `WA_DontShowOnScreen` 让容器完全不参与窗口的子控件绘制流程，
   只在我们显式调用 `render()` 时才被画一次 → **消除了双重绘制**。
2. `render()` 时 painter 已带缩放变换，子控件的字号、线宽、渐变端点
   **全部被等比放大**，4K 屏上文字依然清晰饱满。
3. 窗口尺寸变化时**无需重建缓存**——缓存始终是 1920×1080，
   只改变贴图的目标矩形即可。这是相对方案 A 的额外性能收益。

### 4.3 缓存失效策略

| 触发条件 | 是否重建缓存 | 原因 |
|---|---|---|
| 窗口 `resize` | ❌ 不重建 | 缩放在贴图阶段完成，缓存内容没变 |
| 数据刷新（3 秒一次） | ✅ 重建 | 调用 `invalidateCache()` |
| 地图动画帧（16 ms 一次） | ✅ 重建 | 飞线位置变化 |
| 快捷键 R | ✅ 重建 | 手动强制刷新 |

关键在于地图动画的失效通知机制。地图控件位于离屏容器中，
自身的 `update()` **不会**触发屏幕重绘，因此需要一个回调：

```cpp
// ChinaMapWidget
void setFrameCallback(std::function<void()> cb) { m_onFrame = std::move(cb); }

void ChinaMapWidget::timerEvent(QTimerEvent *) {
    ++m_frame;
    if (m_onFrame) m_onFrame();     // 通知外层把缓存标记为失效
    emit frameRendered(m_frame);
}

// DashboardWidget
m_map->setFrameCallback([this]() { invalidateCache(); });
```

## 5. 图表控件设计

### 5.1 统一的「值 → 像素」映射

所有柱状/折线图共享同一套坐标换算，抽成 `Chart::Config` 统一管理边距与刻度：

```cpp
// ChartTypes.h
struct Config {
    double yMin = 0.0, yMax = 0.0;   // <=0 表示自动
    int    yTicks = 5;
    bool   gridLines = true;
    QColor gridColor = QColor(0x4A, 0x50, 0x7A);
    int    marginLeft = 30, marginRight = 10;
    int    marginTop = 18, marginBottom = 20;
    bool   showValues = true;
};
```

### 5.2 智能刻度上界：`niceAxisMax`

直接用数据最大值当纵轴上界会有两个问题：柱顶贴边、或最高点正好落在网格线上。
解决办法是按 **1 / 2 / 2.5 / 5 / 10** 的步进向上取整，并预留 15% 余量：

```cpp
inline qreal niceAxisMax(qreal rawMax) {
    if (rawMax <= 0.0) return 10.0;
    const int steps = 5;
    const qreal rough = rawMax * 1.15 / steps;      // 留 15% 余量
    const qreal mag = std::pow(10.0, std::floor(std::log10(rough)));
    const qreal norm = rough / mag;
    qreal nice = 10.0;
    if      (norm <= 1.0) nice = 1.0;
    else if (norm <= 2.0) nice = 2.0;
    else if (norm <= 2.5) nice = 2.5;
    else if (norm <= 5.0) nice = 5.0;
    return nice * mag * steps;                      // 一定是 1/2/2.5/5/10 的倍数
}
```

效果：数据最大值 583 → 上界 1000，刻度为 0/200/400/600/800/1000，整数且留有余量。

### 5.3 标签抽稀

31 天的柱状图上，X 轴标签必然重叠。这里做了两处抽稀：

**柱状图**：用 `QFontMetrics` 估算标签宽度，槽位放不下就不画。

```cpp
const QFontMetrics fm(p.font());
if (slotW >= fm.horizontalAdvance(m_categories.value(i)) + 2)
    p.drawText(...);
```

**折线图**：估算标签宽度与槽位宽度的比值，按步长跳着画。

```cpp
const double step = qMax(1.0, std::ceil(
    (fm.horizontalAdvance(QStringLiteral("000")) + 6) / slotW));
if (std::fmod(i, step) < 0.001)
    p.drawText(...);
```

### 5.4 Catmull-Rom 样条平滑

折线图不能用直线段连接——设计稿的曲线是圆润的。但手调贝塞尔控制点会出问题：
数据点增减时曲线形状立刻走样。

Catmull-Rom 的性质是**曲线必定穿过所有数据点，且相邻段切线连续**，完全由数据决定：

```cpp
QPainterPath buildSmoothPath(const QVector<QPointF> &pts, qreal tension = 1.0) {
    path.moveTo(pts.first());
    for (int i = 0; i < n - 1; ++i) {
        const QPointF p0 = (i == 0) ? pts.at(0) : pts.at(i - 1);
        const QPointF p1 = pts.at(i);
        const QPointF p2 = pts.at(i + 1);
        const QPointF p3 = (i + 2 < n) ? pts.at(i + 2) : pts.at(n - 1);

        const QPointF c1 = p1 + (p2 - p0) * (tension / 6.0);
        const QPointF c2 = p2 - (p3 - p1) * (tension / 6.0);
        path.cubicTo(c1, c2, p2);
    }
    return path;
}
```

`tension = 0` 退化为直线，`tension = 1` 为标准 Catmull-Rom，可按需调整曲线张力。

### 5.5 沿圆弧的渐变

**这是 Qt 绘图的一个真实限制**：`QLinearGradient` 只能沿**直线**渐变，
无法沿圆弧渐变。而设计稿的仪表刻度环要求青 → 蓝 → 品红的连续过渡。

解法是**按弧长分段填充**：

```cpp
const int segments = 180;              // 270° / 180 = 1.5°/段
const qreal per = spanDeg / segments;
for (int i = 0; i < segments; ++i) {
    const qreal t = qreal(i) / (segments - 1);
    p.setPen(QPen(sampleGradient(colors, t), lineWidth));
    p.drawArc(box, int((startDeg + per * i) * 16.0), int(per * 16.6));
}
```

**为什么 180 段是合理的**：相邻段的颜色差低于人眼可辨阈值，视觉上连续。
代价是 180 次 `drawArc` 调用，实测在 1920×1080 下耗时 < 0.3ms。

> 补充：Qt 的 `QConicalGradient` 虽然名字像"锥形渐变"，但它是以中心点为原点按**角度**分配颜色，
> 并不沿弧长均匀变化，且两端有硬跳变，不适合做刻度环。

### 5.6 七段数码管

设计稿的数码管有明显的**六边形段体**（两端斜切），而不是简单的粗线段。
斜切角是造型的关键——没有它会显得像"加粗的线"，而不像真实显示器件。

```cpp
// 沿 a→b 生成六边形：两端各有一个斜切角
const qreal cut = qMin(t * 0.40, len * 0.30);
QPolygonF hex;
hex << a + n * (t/2.0)
    << a + dir * cut + n * (t/2.0)      // 起点斜切
    << b - dir * cut + n * (t/2.0)
    << b + n * (t/2.0)
    << b - n * (t/2.0)
    << b - dir * cut - n * (t/2.0)      // 终点斜切
    << a + dir * cut - n * (t/2.0)
    << a - n * (t/2.0);
```

段位用位掩码表示，未点亮的段以 `alpha = 72` 绘制——既能看出数码管的八段式轮廓，
又不会抢走点亮段的视觉焦点（alpha 过低像缺笔画，过高像全亮）。

```cpp
static const quint8 kDigits[10] = {
    0b0111111, 0b0000110, 0b1011011, 0b1001111, 0b1100110,
    0b1101101, 0b1111101, 0b0000111, 0b1111111, 0b1101111
};
//        0:a,b,c,d,e,f  1:b,c  2:a,b,d,e,g ...
```

### 5.7 逐柱异色

「模具零件合格率」和「班组合格率」都是"每个类别一根柱子，按合格/不合格着色"，
而不是"多系列分组"。为此在 `Series` 中增加了 `perBarColors`：

```cpp
struct Series {
    QString name;
    QVector<double> values;
    QColor color;
    bool filled = false;                    // 面积图专用
    QVector<QColor> perBarColors;           // 长度 == categories 时生效
};
```

绘制时自动判定：

```cpp
const bool singleSeries = (m_series.size() == 1);
const bool usePerBarColor = singleSeries
    && m_series.first().perBarColors.size() == groupCount;
const int barCount = singleSeries ? 1 : m_series.size();
```

这样同一个 `GroupedBarChart` 同时支持两种模式，无需拆分成两个类。

## 6. 中国地图与飞线动画

### 6.1 数据来源与合规

数据源为全国行政区划边界 GeoJSON，包含 **34 个省级行政区 + 10 段国界线**，
完整包含台湾省、香港、澳门特别行政区以及国界线。

> **合规说明**：本项目的地图渲染严格遵循以下要求——
> 完整绘制 34 个省级行政区（含台湾省、香港、澳门特别行政区），
> 完整绘制国界线（含南海诸岛国界线与十段线），
> 不遗漏、不简化任何行政区划，不绘制任何军事敏感区域。

### 6.2 离线坐标表的生成

原始 GeoJSON 有 335 KB、10 万+ 顶点，直接嵌入不现实。
`tools/gen_map_data.py` 做三步处理：

```
1. 道格拉斯-普克简化（容差 0.02°）        → 顶点数大幅下降
2. 经纬度量化：× 100 存为 short           → 1 单位 = 0.01° ≈ 1.1 km
3. 扁平化：所有环的顶点连续存放 + 索引表  → 便于 C++ 侧零拷贝读取
```

结果：**34 个行政区 / 121 个环 / 11591 个顶点 / 160 KB**。

生成的数据结构：

```cpp
struct RingSpan { short start; short count; };    // [起始下标, 顶点数)

inline constexpr short kPointPool[11591][2] = {...};   // 扁平顶点池
inline constexpr RingSpan kRingSpans[121] = {...};      // 环索引
inline constexpr const char* kNameTable[34] = {...};    // 行政区名
inline constexpr short kBorderPool[31][2] = {...};      // 国界线
```

**简化算法用迭代式而非递归**——原始数据的最长环有数千顶点，
递归版道格拉斯-普克会有栈溢出风险：

```python
def douglas_peucker(points, tol):
    """迭代式道格拉斯-普克，避免深递归导致栈溢出"""
    stack = [(0, n - 1)]
    while stack:
        first, last = stack.pop()
        ...
```

**一个需要注意的坑**：面积过滤对**多边形**有效（滤掉飞地小碎片），
但对**国界折线**必须跳过——十段线每一段本身都很短小，
按面积过滤会漏掉整段国界线，造成地图画错。

```python
if is_border:
    if len(simplified) < 2: continue        # 折线只按点数过滤
elif len(simplified) < 4 or ring_area(simplified) < MIN_AREA:
    continue                               # 多边形按面积过滤
```

### 6.3 投影变换

采用**等经纬度圆柱投影 + 纬度按 cos(中心纬度) 收缩**：

```cpp
QPointF ChinaMapWidget::project(double lon, double lat) const {
    static const double kLatMid = (MapData::kMinLat + MapData::kMaxLat) / 2.0;
    static const double kCos = std::cos(qDegreesToRadians(kLatMid));

    const double x = (lon - MapData::kMinLon) * kCos
                   / ((MapData::kMaxLon - MapData::kMinLon) * kCos);
    const double y = (MapData::kMaxLat - lat) / (MapData::kMaxLat - MapData::kMinLat);
    return QPointF(x, y);
}
```

**为什么不用 Web 墨卡托**：墨卡托会把高纬度地区拉伸得过大，
在我国国土范围内形变明显（黑龙江、内蒙古会被拉宽）。墨卡托还涉及纬度极点的数学奇点。
等经纬度圆柱投影 + cos 收缩在国土范围内形变更小，且只需一次线性变换，便于说明与验证。

投影结果是 **0~1 的归一化坐标**，再由 `ChinaMapWidget::paintEvent` 通过 `QTransform`
映射到控件矩形。这样控件尺寸变化时只需更新变换矩阵，无需重新计算投影。

### 6.4 世界变换下的线宽补偿

**这是一个容易踩的坑**：在 `setWorldTransform()` 之后绘制，
画笔线宽也会被世界变换缩放。要得到期望的物理线宽，必须乘以缩放的倒数：

```cpp
const qreal invScale = 1.0 / qMax(target.width(), target.height());

p.setWorldTransform(toScreen, false);
p.setPen(QPen(provinceBorder(), 0.9 * invScale));   // ← 乘 invScale
p.drawPolygon(poly);
```

绘制圆点半径、光点大小、箭头尺寸时同样要乘 `invScale`：

```cpp
const qreal baseR = (city.major ? 5.0 : 3.6) * invScale;
```

### 6.5 飞线动画

飞线是二次贝塞尔曲线，弧顶控制点相对中点抬高：

```cpp
const QPointF mid((a.x() + b.x()) / 2.0, (a.y() + b.y()) / 2.0);
const qreal dist = std::hypot(b.x() - a.x(), b.y() - a.y());
const QPointF ctrl(mid.x(), mid.y() - dist * route.curvature);

QPainterPath path;
path.moveTo(a);
path.quadTo(ctrl, b);
```

三层绘制叠加出霓虹效果：

```cpp
// ① 外发光：更粗、更透明的底线
QColor glow = route.color;  glow.setAlpha(60);
p.setPen(QPen(glow, 4.0 * invScale, Qt::SolidLine, Qt::RoundCap));
p.drawPath(path);

// ② 线条本体
p.setPen(QPen(route.color, 1.6 * invScale, Qt::SolidLine, Qt::RoundCap));
p.drawPath(path);

// ③ 流动光点：沿曲线推进，首尾淡出
for (int dot = 0; dot < 3; ++dot) {
    const qreal t = std::fmod(phase + dot / 3.0 + offset, 1.0);
    QColor c(0xD8, 0xFF, 0xFF);
    c.setAlpha(int(230 * std::sin(t * M_PI)));   // sin 保证两端为 0
    p->drawEllipse(path.pointAtPercent(t), 2.4 * invScale, 2.4 * invScale);
}
```

**流光的两个细节**：
1. 每条线路**错开相位**（`offset = i / routes.size()`），
   形成"同时有多批货在途"的观感，而不是所有光点同步前进。
2. 透明度用 `sin(t·π)` 而非线性函数，保证光点到达终点时透明度归零，
   不会"啪"一下消失。

### 6.6 城市节点涟漪

```cpp
for (int layer = 0; layer < 2; ++layer) {
    const qreal t = std::fmod(phase + layer * 0.5, 1.0);
    const qreal rr = baseR * (1.0 + t * 3.4);       // 半径按比例放大
    QColor c = cityGlow();
    c.setAlpha(int(120 * (1.0 - t)));               // 透明度线性淡出
    p->setPen(QPen(c, 1.2 * invScale));
    p->drawEllipse(np, rr, rr);
}
```

两层涟漪相差半个周期，产生连续的扩散波。

### 6.7 越界保护

坐标表由脚本生成，若生成脚本有 bug，C++ 侧的越界读会导致崩溃。
因此在构建时做了双重检查：

```cpp
const int endIdx = int(span.start) + int(span.count);
if (span.start < 0 || endIdx > int(MapData::kPointPoolRows)) {
    qWarning("ChinaMapWidget: ring %d out of range (%d..%d)", i, ...);
    continue;      // 宁可少画一个环，也不能越界读
}
```

同时把循环变量从 `short` 改为 `int`——虽然当前数据量（11591）远小于
`SHRT_MAX`（32767）不会溢出，但显式用 `int` 更安全，也避免隐式提升带来的误解。

## 7. 数据层设计

### 7.1 数据模型

`DashboardData` 是纯数据容器，不含任何绘制逻辑：

```cpp
struct DashboardData {
    // 当月计划达成率
    double moldPlanRate = 83.0;
    int    moldPlanTarget = 100, moldAchieved = 83, partTotal = 4027;

    QStringList partCategories;          // 模仁 / 零件 / 辅件 / 电极
    QVector<double> partPlan, partActual;

    // 每日工序达成数
    QStringList dayLabels;                // 1..31
    QVector<QVector<double>> dailyProcesses;   // 每天 3 个工序

    // ... 年度产量、模具进度、合格率、品质管理 ...
};
```

### 7.2 模拟数据的三种算法

模拟数据不能简单用 `qrand() % 100`——那样数值会剧烈跳变，不像真实产线。
本项目实现了三种更真实的算法：

**① 有界随机游走**（产量类指标）

```cpp
double DataSimulator::jitter(double current, double base, double amplitude, rng) {
    const double delta = (rng->generateDouble() - 0.5) * 2.0 * amplitude;
    double next = current + delta;
    return qBound(base * 0.85, next, base * 1.15);   // 硬性夹在 ±15% 内
}
```

以基准值为中心小幅游走，且硬性限制在 ±15% 区间内 → "有变化但不跳变"。

**② 偏斜分布**（合格率类指标）

真实合格率天然聚集在 80~95 区间，用均匀分布会得到大量低于 60% 的不合理值：

```cpp
double DataSimulator::skewedHigh(double min, double max, double mean, rng) {
    const double r = rng->generateDouble();
    const double skew = (r - 0.5) + (rng->generateDouble() - 0.5) * 0.6;
    return qBound(min, mean + skew * 12.0, max);
}
```

两个均匀分布叠加得到**三角分布**，天然聚集在 `mean` 附近。

**③ 周末效应**（每日产出）

```cpp
const bool weekend = (day % 7 == 5 || day % 7 == 6);
const double factor = weekend ? 0.72 : 1.0;      // 周末产能降至 72%
```

### 7.3 刷新策略

不是每 3 秒刷新所有数据，而是**按数据的变化频率分层**：

| 数据 | 刷新频率 | 理由 |
|---|---|---|
| 当月达成率 | 每 9 秒（3 tick）且**单调递增** | 真实产线的累计达成只会上升 |
| 每日工序达成数 | 只更新**当天**（第 31 天） | 历史数据不应变动 |
| 月度趋势 | 每 2 tick 随机更新一段 | 模拟"新月份数据回填" |
| 15 天合格率 | 只更新**最后一天** | 同上 |
| 零件总数 | 每 tick 微增 0~5 | 持续累加 |

这个设计让看板在 3 秒刷新时**看不出机械重复**，同时保证逻辑合理
（如达成率不会倒退），细节上贴近真实业务。

## 8. 性能优化

### 8.1 优化点汇总

| 优化项 | 做法 | 效果 |
|---|---|---|
| **坐标预构建** | 地图投影与 `QPolygonF` 构建只在构造时做一次 | 每帧只做 painter 变换，省去 1.1 万次投影计算 |
| **离屏缓存** | 内容渲染到 1920×1080 `QImage`，窗口 resize 不重建 | resize 从 O(全量重绘) 降到 O(一次贴图) |
| **脏标记** | 仅数据刷新/动画帧才 `invalidateCache()` | 静止时 0 绘制开销 |
| **圆弧分段** | 180 段近似沿弧渐变 | < 0.3ms |
| **抗锯齿范围** | 只在图表控件开启 `Antialiasing` | 文字绘制不额外抗锯齿，省 30% 文本渲染时间 |
| **数据拷贝最小化** | `setData()` 传 `const&`，控件内部按值存储 | 避免 20+ 控件重复拷贝 |
| **标签抽稀** | 用 `QFontMetrics` 预判，避免超量 `drawText` | 31 天折线图每帧少画 20+ 次文本 |

### 8.2 渲染调用次数估算

以地图动画的一帧（1920×1080）为例：

| 项目 | 调用次数 |
|---|---|
| 省界多边形 | 121 |
| 国界线折线 | 10 |
| 飞线（本体 + 发光） | 5 × 2 = 10 |
| 流光点 | 5 × 3 = 15 |
| 城市涟漪 | 6 × 2 = 12 |
| 圆弧分段（仪表 ×2） | 180 + 120 = 300 |
| 其他图表 | ~200 |
| **合计** | **~700** |

700 次绘制调用在 CPU 渲染下约 **8~15 ms/帧**，可稳定 60fps。
开启 GPU 加速（`QSG_RHI_BACKEND` / DirectComposition）后可进一步降低。

### 8.3 未来可优化点

1. **QPixmap 缓存地图图层**：省界轮廓是静态的，可预渲染成一张图，只在窗口尺寸变化时重绘。
   这能把每帧的 121 次多边形填充降到 1 次位图贴图。
2. **动画降级**：检测到低性能设备时（如连续 3 帧超过 25ms）自动把 60fps 降到 30fps。
3. **GPU 绘制路径**：用 `QOpenGLWidget` + `QOpenGLPaintDevice` 走 GPU 光栅化。

## 9. 踩坑记录

本节记录开发中真实遇到并解决的问题，是项目最有价值的部分。

### 9.1 MSVC 下 `M_PI` 未定义

```cpp
// ❌ 编译失败：MSVC 的 <cmath> 默认不定义 M_PI
const qreal angle = std::atan2(dir.y(), dir.x()) * 180.0 / M_PI;

// ✅ 改用 Qt 自己的换算函数，无需任何编译宏
const qreal angle = qRadiansToDegrees(std::atan2(dir.y(), dir.x()));
const double kCos = std::cos(qDegreesToRadians(kLatMid));
```

> 另一种解法是在 CMake 里加 `target_compile_definitions(... _USE_MATH_DEFINES)`，
> 但改用 Qt API 更干净，且跨编译器行为一致。

### 9.2 `QString::number` 没有三参整数重载

```cpp
// ❌ 编译失败：整数版只有 2 参
QString::number(d.machiningMolds, 10, 3);

// ✅ 整数
QString::number(d.machiningMolds);
// ✅ 固定 3 位，不足补零（数码管需要）
QString::number(d.machiningMolds, 10).rightJustified(3, QChar('0'));
```

### 9.3 缩放方案的双重绘制（最隐蔽的问题）

见第 4.2 节。现象是在 2560×1440 上会看到左上角有一块 1920×1080 的
"未缩放矩形边界"。根因是 Qt 会在自定义 `paintEvent` 返回后
用子控件原生几何再绘制一遍。

**排查思路**：先怀疑 QPainter 变换，再检查 `QWidget::render()` 文档中
关于"子控件也会被绘制"的说明，最后定位到 `WA_DontShowOnScreen`。

### 9.4 仪表文字与指针重叠

初版把「零件数」和数值放在圆心附近，指针扫过时与文字糊成一团。
修复思路：**把文字放在指针扫不到的位置**——270° 仪表的缺口在正下方，
所以把文字下移到下半区，正好落在缺口方向：

```cpp
// 放在 270° 缺口方向（正下方），指针永远扫不到
p.drawText(QRectF(center.x() - radius, center.y() + radius * 0.30, ...), ...);
```

### 9.5 单系列多柱的语义歧义

初版实现「班组合格率」时，传入 6 个 `Series`（每个含 1 个值）+ 6 个类别，
结果画出了 36 根柱子。正确做法是**单系列 + 逐柱配色**，
为此在 `Series` 中新增 `perBarColors` 字段，并让 `GroupedBarChart`
自动判定渲染模式。

### 9.6 国界线被面积过滤误删

道格拉斯-普克简化后加了一道面积过滤，用来剔除飞地小碎片。
但十段线的每一段本身都短小，按面积过滤导致**整段国界线消失**。

修复：折线类型跳过面积过滤，只按顶点数判断。

### 9.7 世界变换下的线宽失真

```cpp
p.setWorldTransform(transform, false);   // 缩放了 826x
p.setPen(QPen(color, 1.2));              // 这根线的实际屏幕宽度 = 1.2 * 826！
```

所有在世界坐标系下的线宽、圆点半径都必须乘以缩放倒数 `invScale`。

### 9.8 死代码的及时清理

第一版有一个 `Panel` 基类（提供标题栏 + 外框），但最终所有面板
（`TitlePanel` / `StatPanel` / `DataTablePanel`）都直接继承 `QWidget`，
`Panel` 成了死代码。已连同 CMakeLists 中的引用一并删除——
留在项目里会让阅读者困惑于"到底该继承哪个"。

### 9.9 `WA_OpaquePaintEvent` 会跳过调色板背景填充（影响面最大的一处）

**现象**：整屏 20 多个面板全部变成浅灰底色（`#F0F0F0`），上面的白字几乎
不可见；而面板标题栏（自绘 `fillRect`）颜色正常。只有把截图和原图并排比对，
才能看出问题是"面板底色根本没被画出来"，而不是"文字颜色配错了"。

**根因**：面板宿主控件用了 `setAutoFillBackground(true)` + `QPalette::Window`
来设置底色，同时又为了少做无用功声明了 `WA_OpaquePaintEvent`。
但 Qt 对声明了该属性的控件会认为"它自己会画满整个区域"，
于是**跳过由调色板触发的背景填充**——底色一次都没被绘制，
露出的是离屏容器 `m_content` 的默认浅色。

```cpp
// ❌ 底色永远不会出现：WA_OpaquePaintEvent 让调色板填充被跳过
w->setAutoFillBackground(true);
pal.setColor(QPalette::Window, Theme::panelBody());
w->setPalette(pal);
w->setAttribute(Qt::WA_OpaquePaintEvent, true);

// ✅ 显式自己画，行为与渲染路径无关
class PanelHost : public QWidget
{
protected:
    void paintEvent(QPaintEvent *) override
    {
        QPainter p(this);
        p.fillRect(rect(), Theme::panelBody());
    }
};
```

**教训**：只要声明了 `WA_OpaquePaintEvent`，就必须真的把每个像素画满，
不能再指望 Qt 帮忙填背景。同时给离屏容器也设了
`QPalette::Window = Theme::background()` 作为兜底，避免任何漏画处露出浅色。

### 9.10 同尺寸兄弟控件触发遮挡剔除：环图完全不显示

**现象**：「模具达成率」面板里的进度环一点都没画出来，但同面板的文字正常。

**排查**：给 `ProgressRing::paintEvent` 临时加一层半透明品红
`fillRect`，重新截图后发现**一个品红像素都没有** —— 说明
`paintEvent` 根本没有被调用，问题不在绘制逻辑而在绘制调度。

**根因**：环图与文本面板 `StatPanel` 的几何**完全重合**，
而 `StatPanel` 在控件树里排在后面（绘制顺序在后）且声明了
`WA_OpaquePaintEvent`。Qt 判定"后者会完全覆盖前者"，
于是把前面的环图整块跳过了。

**修复**：按参考图实测尺寸把两者错开（环直径 63px 居左、文本移右侧）。
教训：**不要让控件几何重叠**；确实需要层叠时，被压住的控件
不能声明不透明。

### 9.11 `drawArc` 的角度约定与屏幕坐标系相反

**现象**：「当天合格率」的半圆刻度盘只看到中间的数字，弧线、刻度线、
进度圆点全部消失。

**根因**：同一个 `paintEvent` 里混用了两套角度约定——
刻度线 / 标签 / 圆点用 `center + (cos, -sin) * r`（屏幕坐标，y 轴向下），
而弧线交给了 `QPainter::drawArc`。`drawArc` 用的是数学约定：
0° 在 3 点方向、**逆时针为正、y 轴向上**。于是弧线被画到了圆心下方的
另一半圆上；而圆心定在 `height() * 0.90`，整条弧都落到控件之外被裁掉了。

```cpp
// ✅ 统一到屏幕坐标系：0° = 12 点方向，顺时针为正
inline QPointF polar(const QPointF &c, qreal r, qreal deg)
{
    const qreal rad = qDegreesToRadians(deg);
    return QPointF(c.x() + std::sin(rad) * r, c.y() - std::cos(rad) * r);
}
// 弧线也改成沿弧长取点逐段连线（顺便实现沿弧渐变），不再用 drawArc
```

**教训**：一个控件内部只允许存在一套角度约定；跨 API 混用之前，
先确认对方用的是哪个坐标系。

### 9.12 饼图被"双重 90° 偏移"

**现象**：饼图只画出了一部分扇形，扇区之间互相重叠，并且留下一道缺口。

**根因**：起始角写成 `qreal startAngle = 90.0 * 16.0;`（注释说这是
"12 点方向的起始角，顺时针为正"），但传给 `drawPie` 时又叠加了一次换算
`int(startAngle + 90.0 * 16.0)` —— 整体多转了 90°；同时扇区累计角与
标签位置用的是两套不同的角度制，于是出现"重叠 + 缺口"。

**修复**：统一为「0° = 12 点、顺时针为正」，再换算到
`QPainterPath::arcTo` 的约定（`a = 90 - deg'`，扫描角取负）：

```cpp
qreal startDeg = 0.0;                       // 0° = 12 点方向
for (const Chart::PieSlice &slice : m_slices) {
    const qreal spanDeg = slice.value / total * 360.0;
    QPainterPath path;
    path.moveTo(center);                    // 先落到圆心
    path.arcTo(box, 90.0 - startDeg, -spanDeg);   // 半径线 + 外弧
    path.closeSubpath();                    // 回到圆心，闭合成扇区
    startDeg += spanDeg;
}
```

顺带按参考图补上了"扇区名 + 百分比"两行标签，并用
`color.lightness()` 自动在黑白字之间切换以保证对比度。

### 9.13 七段数码管的两个布局错误

**现象**：数码管读不出数字，四个字看起来都像"日"。

两个互相独立的原因：

1. **未点亮段的 alpha 过高**。熄灭段用 `alpha = 40` 绘制，
   7 段全部显形，每个数字都变成"8"。设计稿里熄灭段几乎看不见，
   改为 `alpha = 16`。
2. **竖段端点内缩量取错**。竖段可用长度只有 `h/2`，而内缩量写成了
   `qMax(t, h * 0.055)`，其中 `t ≈ cellW * 0.135`。控件偏扁时 `t`
   接近甚至超过 `h/2`，两端各内缩 `t` 之后整根竖段只剩几个像素，
   数字退化成"三条横杠"。改为按半高比例取：`vInset = h * 0.06`。

另外字宽不能直接拿 `width() / n` —— 真实数码管高约为宽的 1.6 倍，
应按宽高比反推尺寸，宽度不足时再整体等比收缩。同时对
`digitValue()` 返回 -1 的非数字字符做了越界保护。

### 9.14 水平条形图的数值被裁成一个字符

**现象**：「模具产量」的数值 45 / 18 / 19 全部只显示第一位数字。

**根因**：数值标签画在条形右侧，宽度直接取自 `cfg.marginRight`：

```cpp
const int valueW = cfg.marginRight;                        // 默认值只有 10
p.drawText(QRectF(bar.right() + 3, ..., valueW - 4, ...));  // 实际只剩 6px
```

而 `Chart::Config` 的 `marginRight` 默认是 10，装配时又只设置了
`marginLeft`，于是标签框只有 6px 宽，两位数被硬裁。

**修复**：装配时显式给足数值栏宽度，并在控件内部用 `QFontMetrics`
实测字宽兜底，避免再次因为配置漏填而静默裁字。

### 9.15 用"离屏截图模式"做自动化视觉验证

本项目没有设计师在旁校对，"渲染结果是否符合设计稿"只能自己闭环验证。
靠肉眼看整图缩略图很容易漏掉"底色不对"这类系统性问题，
于是给 `main.cpp` 加了一个 `--shot <path>` 开关：以 1920×1080 显示、
等待首帧布局与离屏缓存构建完成（900ms）、`grab()` 保存 PNG 后自动退出。

```cpp
if (!shotPath.isEmpty()) {
    w.resize(1920, 1080);
    w.show();
    QTimer::singleShot(900, &app, [&w, &app, shotPath]() {
        w.grab().save(shotPath);
        app.quit();
    });
}
```

再配合一段 Python 脚本，把截图与设计稿按同一坐标裁剪、并排拼图放大对比，
才逐步定位到 9.9 ~ 9.14 这些在整图缩略图上根本看不出来的问题。

这套「加开关 → 离屏截图 → 与原图同坐标并排比对」的流程，
让整个还原工作在没有第三方的条件下也能形成闭环验证，
也是本项目最值得复用的工程经验。

## 12. 面试问答准备

### Q1：为什么用 QPainter 自绘而不用 QtCharts？

**答**：
1. `QtCharts` 模块在 Qt 6 已不再积极维护，官方建议新项目另选方案。
2. 样式定制能力不足。本项目需要的沿圆弧渐变刻度、双层发光、
   七段数码管的六边形段体、逐柱异色等效果，用 QChart 需要覆盖其 private 字段，
   跨 Qt 版本极易失效。
3. 自绘能精确控制绘制顺序与状态设置，20+ 图表同屏刷新时性能更可控。

代价是约 2000 行代码，收益是表现力无上限 + 零第三方依赖。

### Q2：大屏怎么适配不同分辨率？

**答**：采用「设计分辨率 1920×1080 + 离屏渲染 + 等比缩放」。

关键在于**离屏容器 + `WA_DontShowOnScreen`**：
把面板放在一个不参与窗口自动绘制的容器里，用 `render()` 渲染到 1920×1080 的
`QImage`，再按 `min(w/1920, h/1080)` 缩放后居中贴到屏幕，多余部分留黑边。

我一开始的实现是直接在 `paintEvent` 里对 painter 做 `scale()`，
但发现**面板是真实 QWidget 子窗口，不参与这个变换**——
Qt 会在 `paintEvent` 返回后用原生几何再画一遍，
在 2560×1440 上出现了「缩放版 + 未缩放版」的双重画面。
用 `render()` 既解决了双重绘制，又让字号和线宽也跟着等比放大
（如果只是 `setGeometry` 缩放，文字在 4K 上会显得又小又细）。

### Q3：地图数据怎么处理的？

**答**：原始 GeoJSON 335 KB、10 万+ 顶点，不能直接嵌入。
用 Python 预处理成紧凑的 C++ 数组：
道格拉斯-普克简化（容差 0.02°）→ 经纬度×100 量化存为 `short` → 扁平化 + 索引表。
最终 34 个行政区 / 121 个环 / 11591 顶点 / 160 KB。

投影用等经纬度圆柱 + 纬度按 cos(中心纬度) 收缩，
不用 Web 墨卡托——墨卡托会把高纬度拉得过大，在我国范围内形变明显。

C++ 侧在构造时一次性完成投影并缓存 `QPolygonF`，每帧只做 painter 变换。

另外有两个坑：一是道格拉斯-普克必须用**迭代式**，递归版在长环上会栈溢出；
二是面积过滤对多边形有效但**必须跳过折线**，否则十段线会被整段删掉。

### Q4：圆弧怎么实现渐变？

**答**：`QLinearGradient` 只能沿直线渐变，无法沿圆弧。
解法是按弧长分段：把 270° 分成 180 段，每段 1.5°，
每段的颜色按其在弧上的位置采样渐变。相邻色差低于人眼可辨阈值，
视觉上就是连续渐变。代价是 180 次 `drawArc`，实测 < 0.3ms。

顺带一提，Qt 的 `QConicalGradient` 虽然名字像"锥形渐变"，
但它按**角度**分配颜色而不是沿弧长，且两端有硬跳变，不适合做刻度环。

### Q5：为什么模拟数据要用随机游走而不是随机数？

**答**：因为大屏是长时间挂着看的。如果用 `qrand() % 100`，
数值会剧烈跳变，一眼就看出是假数据。

我实现了三种算法：
① **有界随机游走**——以基准值为中心小幅游走，硬性夹在 ±15% 内，
   实现"有变化但不跳变"；
② **偏斜分布**——合格率用两个均匀分布叠加得到三角分布，
   天然聚集在 80~95，模拟真实的高合格率特征；
③ **周末效应**——第 6、7 天产能降到 72%。

另外刷新策略是分层的：每日数据只更新"当天"，历史数据不动；
累计达成率单调递增不倒退。这些细节让看板在 3 秒刷新时看不出机械重复。

### Q6：项目怎么保证代码质量？

**答**：本机没有 Qt 环境，无法编译，所以做了几件事：

1. **两轮独立的静态代码审查**。第一轮发现 4 个问题：
   `QString::number` 三参重载不存在、MSVC 下 `M_PI` 未定义、
   头文件缺 `QStringList`、以及最重要的缩放双重绘制。
   第二轮复核时又发现了双重绘制的**衍生问题**（离屏容器仍会被 Qt 自动绘制）。
   两轮共修复 6 个问题，全部是编译期或运行期的硬错误。

2. **用 Python 复刻了一份渲染实现做视觉验证**。
   因为无 Qt 无法运行，我用相同坐标表、配色和算法写了个 PIL 版本，
   渲染出静态大屏图。它实际帮助发现了
   "仪表文字与指针重叠"、"数码管熄灭段过暗"两个视觉缺陷——
   这两个问题纯靠读代码是看不出来的。

3. **生成期校验**。坐标表由脚本生成，脚本里有面积过滤和断言；
   C++ 侧又有运行时越界检查，形成双重保险。

### Q7：如果让你重做，会怎么改进？

**答**：

1. **地图图层位图缓存**。省界轮廓是静态的，可以预渲染成一张位图，
   每帧从 121 次多边形填充降到 1 次贴图。这是当前最大的性能优化空间。

2. **引入 Qt Quick / QML**。如果需求后续可能变成"多屏联动"或"图表可交互"
   （点击柱状图下钻明细），QML 的声明式 + 状态管理更合适。
   但对于当前这种"布局固定、纯展示"的大屏，Widgets + QPainter 更直接。

3. **数据层做缓存与断线重连**。当前模拟数据源是理想化的，
   真实场景需要处理网络抖动、后端超时、数据乱序等问题。

4. **加自动化测试**。可以写 Qt Test 单元测试验证
   `niceAxisMax`、`buildSmoothPath`、`project` 等纯函数的正确性。
